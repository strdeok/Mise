# Mise Table 기능 명세서

## 1. 문서 목적

이 문서는 Expo 기반 Mise Table 모바일 앱과 Node.js 서버의 MVP 기능 명세다.

Mise Table은 Todo, 하루 시간표, Focus와 Break 세션, 계획 대비 실제 시간 통계를 하나의 작업 흐름으로 연결한다.

MVP 지원 플랫폼은 iOS와 Android다. 웹과 데스크탑 앱은 현재 범위에 포함하지 않는다.

## 2. 우선순위

| 우선순위 | 의미 |
| --- | --- |
| P0 | 핵심 사용자 흐름에 필요한 MVP 필수 기능 |
| P1 | MVP 후반 또는 출시 품질에 중요한 기능 |
| P2 | 핵심 흐름 검증 후 확장 가능한 기능 |
| P3 | 장기 확장 기능 |

## 3. 기술 범위

### 3.1 App

```text
Expo
React Native
TypeScript
Expo Router
TanStack Query
Zustand
Expo SecureStore
Expo Notifications
```

### 3.2 Server

```text
Node.js
NestJS
TypeScript
REST API
JWT Access Token
Refresh Token
```

### 3.3 Database

```text
PostgreSQL
Prisma ORM
```

### 3.4 기본 원칙

- App은 DB에 직접 접근하지 않는다.
- 서버 API가 모든 사용자 데이터의 진입점이다.
- TanStack Query는 서버 상태를 관리한다.
- Zustand는 화면 전역에서 필요한 로컬 UI 상태를 관리한다.
- 인증 토큰 등 민감한 로컬 값은 SecureStore를 사용한다.
- Redis는 MVP 범위에 포함하지 않는다.

## 4. 앱 구조

### 4.1 메인 탭

```text
Today
Schedule
Stats
Settings
```

### 4.2 전역 미니 타이머

실행 중 세션이 있을 때 메인 화면 하단에 미니 타이머를 표시한다.

표시 항목:

- Todo 제목 또는 Break 종류
- 남은 시간 또는 경과 시간
- running 또는 paused 상태
- Timer 전체 화면 진입

Timer는 고정 Bottom Tab이 아니라 실행 상태에 따라 전역에서 접근하는 화면으로 구성한다.

## 5. 인증

### 5.1 회원가입

우선순위: P0

요구사항:

- 이메일과 비밀번호로 가입할 수 있다.
- 이메일 중복 가입을 막는다.
- 비밀번호 정책 위반 시 오류를 표시한다.
- 가입 성공 후 로그인 가능한 상태가 된다.
- 사용자 기본 settings를 생성한다.

MVP 후반 P1에서 소셜 로그인을 추가할 수 있다.

### 5.2 로그인

우선순위: P0

요구사항:

- 이메일과 비밀번호로 로그인한다.
- 성공 시 Access Token과 Refresh Token을 발급한다.
- 앱은 인증 정보를 안전한 로컬 저장소에 보관한다.
- 앱 재실행 시 유효한 세션을 복원한다.
- 인증 성공 후 Today로 이동한다.

예외:

- 인증 정보가 잘못된 경우 일반적인 로그인 실패 메시지를 표시한다.
- Access Token이 만료되면 Refresh Token으로 갱신을 시도한다.
- 갱신할 수 없으면 인증 정보를 제거하고 로그인 화면으로 이동한다.

### 5.3 로그아웃

우선순위: P0

- 현재 기기의 인증 정보를 제거한다.
- 서버의 Refresh Token을 무효화한다.
- 사용자 데이터 자체는 삭제하지 않는다.
- 로그아웃 후 보호된 화면에 접근할 수 없다.

## 6. Today

### 6.1 Today 화면

우선순위: P0

목적:

앱 진입 후 오늘 해야 할 일과 현재 작업 상태를 한 화면에서 확인하고 바로 집중을 시작한다.

표시 항목:

- 오늘 날짜
- 오늘 총 Focus 시간
- 현재 실행 중 세션
- 다음 Schedule Block
- 오늘 Todo 목록
- Todo별 오늘 기록 시간
- 완료 여부
- 시간표 배치 여부
- 빠른 Todo 추가

행동:

- Todo 생성
- Todo 완료와 완료 취소
- Todo 상세 진입
- Todo에서 Focus 시작
- 다음 Schedule Block에서 Focus 시작
- Schedule 화면 이동

### 6.2 오늘 Todo 기준

Todo 자체와 오늘 사용 여부를 분리해 관리할 수 있어야 한다.

- 장기 Todo가 여러 날짜에 걸쳐 존재할 수 있다.
- 특정 Todo를 오늘 할 일로 지정할 수 있다.
- Schedule Block에 오늘 배치된 Todo는 Today에서 식별할 수 있다.
- 완료된 Todo도 과거 기록에는 유지한다.

## 7. Todo

### 7.1 Todo 계층

우선순위: P0

Todo depth는 0, 1, 2만 허용한다.

```text
depth 0: 프로젝트 또는 큰 작업
depth 1: 작업
depth 2: 세부 작업
```

예시:

```text
Mise Table 개발
└─ Timer 구현
   ├─ 세션 API 구현
   └─ 알림 연결
```

### 7.2 Todo 생성

우선순위: P0

입력:

- title 필수
- description 선택
- parentId 선택
- today 포함 여부

규칙:

- title은 공백만 입력할 수 없다.
- parent가 없으면 depth 0이다.
- depth 2 아래에 자식을 생성할 수 없다.
- 생성 후 관련 Todo 목록을 갱신한다.

### 7.3 Todo 수정

우선순위: P0

- 제목 수정
- 설명 수정
- 부모 변경
- 순서 변경
- 오늘 할 일 포함 여부 변경
- 완료 상태 변경

부모 변경 규칙:

- 자기 자신을 부모로 지정할 수 없다.
- 자기 하위 Todo를 부모로 지정할 수 없다.
- 이동 후 어떤 노드도 depth 2를 초과할 수 없다.
- 부모 변경은 서버에서 계층 제약을 다시 검증한다.

### 7.4 Todo 완료

우선순위: P0

- 사용자가 직접 완료한다.
- 세션 완료만으로 Todo를 자동 완료하지 않는다.
- 계획한 시간이 끝나도 자동 완료하지 않는다.
- 완료된 Todo를 다시 미완료로 변경할 수 있다.
- 완료 Todo의 과거 세션은 유지한다.

### 7.5 Todo 삭제

우선순위: P0

삭제는 soft delete를 기본으로 한다.

- 삭제 전 확인한다.
- 하위 Todo가 있는 경우 함께 목록에서 제거됨을 안내한다.
- 실행 중 Focus가 연결된 Todo는 삭제할 수 없다.
- 삭제 후 과거 세션과 통계 기록은 유지한다.
- 삭제된 Todo의 과거 기록은 제목 스냅샷 또는 삭제된 상태를 구분해 표시할 수 있어야 한다.

### 7.6 Todo 시간 합산

우선순위: P0

완료되거나 저장된 Focus 세션만 기본 통계에 포함한다.

```text
Mise Table 개발
└─ Timer 구현
   ├─ API 구현: 40분
   └─ 알림 연결: 20분
```

이 경우:

```text
Timer 구현 하위 합산 = 60분
Mise Table 개발 하위 합산 = 60분
```

상위 Todo에서 직접 기록한 Focus가 30분이면:

```text
Mise Table 개발 직접 기록 = 30분
하위 합산 = 60분
총 기록 = 90분
```

Stats에서는 직접 기록과 하위 합산을 구분할 수 있어야 한다.

## 8. Schedule

### 8.1 Day View

우선순위: P0

- 하루 단위 시간표를 표시한다.
- 이전 날짜와 다음 날짜로 이동할 수 있다.
- 날짜 선택기로 특정 날짜로 이동할 수 있다.
- 시간 블록을 시간 순서대로 표시한다.
- 현재 시각을 식별할 수 있다.

모바일 MVP에서는 탭 기반 생성과 편집을 기본으로 한다.

### 8.2 Schedule Block 생성

우선순위: P0

입력:

- date
- startAt
- endAt
- todoId 선택
- title 선택
- note 선택

규칙:

- endAt은 startAt보다 늦어야 한다.
- 최소 계획 단위는 5분으로 한다.
- Todo 없이 임시 계획 블록을 생성할 수 있다.
- Todo를 연결하면 기본 title은 Todo 제목을 사용한다.
- 동일 시간대 블록 겹침은 허용하되 UI에서 겹침을 알 수 있어야 한다.

### 8.3 Schedule Block 수정

우선순위: P0

- 날짜 변경
- 시작 시각 변경
- 종료 시각 변경
- 연결 Todo 변경
- 제목 변경
- 메모 변경

### 8.4 Schedule Block 삭제

우선순위: P0

- 삭제 전 확인한다.
- Block 삭제는 연결 Todo를 삭제하지 않는다.
- 이미 생성된 Session 기록을 삭제하지 않는다.
- 과거 Session이 참조하던 Block 삭제 정책은 서버 데이터 무결성을 유지해야 한다.

### 8.5 제스처 편집

우선순위: P1

- 블록 이동
- 블록 길이 변경
- 모바일 스크롤과 제스처 충돌 방지

P0에서는 제스처가 없어도 모든 Schedule 기능을 사용할 수 있어야 한다.

## 9. Timer와 Session

### 9.1 Session 종류

```text
FOCUS
SHORT_BREAK
LONG_BREAK
```

### 9.2 Session 상태

```text
RUNNING
PAUSED
COMPLETED
DISCARDED
```

idle은 DB Session 상태가 아니라 실행 중 Session이 없는 App UI 상태로 취급한다.

### 9.3 Focus 시작

우선순위: P0

시작 경로:

- Today의 Todo
- Todo 상세
- Schedule Block

요구사항:

- Focus는 반드시 Todo에 연결한다.
- 사용자가 목표 시간을 설정할 수 있다.
- 기본값은 settings의 defaultFocusMinutes를 사용한다.
- 5분 단위 선택을 기본 UI로 제공한다.
- Schedule Block에서 시작하면 scheduleBlockId를 저장한다.
- Todo에서 직접 시작하면 scheduleBlockId는 null이다.
- 사용자 기준 RUNNING 또는 PAUSED Session은 동시에 하나만 허용한다.

기본 Focus 시간은 25분이다.

### 9.4 Break 시작

우선순위: P0

- Short Break 기본값 5분
- Long Break 기본값 15분
- Break는 Todo 연결을 요구하지 않는다.
- 직전 Focus의 previousSessionId를 가질 수 있다.
- Focus 완료 후 바로 Break를 선택할 수 있다.
- 사용자가 직접 Break를 시작할 수도 있다.

### 9.5 타이머 표시

우선순위: P0

- 현재 Session 종류
- 연결된 Todo
- 목표 시간
- 남은 시간 또는 경과 시간
- 현재 상태
- Pause 또는 Resume
- Complete
- Discard

사용자는 설정에 따라 countdown 또는 elapsed 표현을 선택할 수 있다.

### 9.6 시간 계산

우선순위: P0

타이머 정확성은 JavaScript interval의 누적 횟수에 의존하지 않는다.

주요 데이터:

```text
startedAt
pausedAt
accumulatedSeconds
targetSeconds
endedAt
durationSeconds
status
```

RUNNING 상태의 경과 시간은 개념적으로 다음과 같이 계산한다.

```text
accumulatedSeconds + (현재 시각 - startedAt)
```

PAUSED 상태에서는 accumulatedSeconds를 사용한다.

클라이언트 interval은 화면을 1초마다 다시 그리기 위한 UI 수단이며 기록의 기준이 아니다.

### 9.7 Pause

우선순위: P0

- RUNNING Session만 Pause할 수 있다.
- 현재까지 경과 시간을 accumulatedSeconds에 반영한다.
- status를 PAUSED로 변경한다.
- pausedAt을 기록한다.
- 기존 종료 알림을 취소한다.

### 9.8 Resume

우선순위: P0

- PAUSED Session만 Resume할 수 있다.
- 새로운 startedAt을 기록한다.
- status를 RUNNING으로 변경한다.
- 남은 목표 시간을 기준으로 종료 알림을 다시 예약한다.

### 9.9 Complete

우선순위: P0

- RUNNING 또는 PAUSED Session을 완료할 수 있다.
- 실제 기록할 durationSeconds를 확정한다.
- endedAt을 기록한다.
- status를 COMPLETED로 변경한다.
- 예약된 종료 알림을 제거한다.
- Focus 완료 후 Short Break, Long Break, 다음 Focus 선택을 제공한다.
- Focus 완료만으로 Todo를 자동 완료하지 않는다.

목표 시간이 끝났더라도 사용자가 즉시 앱을 열지 않을 수 있으므로 목표 시각 도달과 DB의 COMPLETED 상태를 동일하게 취급하지 않는다. 앱이 다시 활성화되었을 때 사용자에게 완료 또는 계속 기록 여부를 처리할 수 있는 흐름을 제공한다.

### 9.10 Discard

우선순위: P0

- RUNNING 또는 PAUSED Session을 폐기할 수 있다.
- 확인 후 status를 DISCARDED로 변경한다.
- discardedAt을 기록한다.
- 예약된 종료 알림을 제거한다.
- 기본 통계에서 제외한다.

### 9.11 중단된 Focus 저장

우선순위: P0

목표 시간 전에 작업을 끝내는 경우 현재까지 실제 작업한 시간을 COMPLETED Session으로 저장할 수 있다.

- 현재 경과 시간을 durationSeconds로 확정한다.
- 1분 미만 기록은 저장 전에 확인할 수 있다.
- 저장하지 않으면 Discard 처리한다.

### 9.12 실행 Session 단일성

우선순위: P0

한 사용자에게 RUNNING 또는 PAUSED 상태의 활성 Session은 최대 하나다.

- 새 Session 시작 전 서버에서 활성 Session을 검사한다.
- 이미 존재하면 새 Session을 생성하지 않는다.
- 서버는 동시 요청에도 이 규칙이 깨지지 않도록 트랜잭션과 DB 제약을 사용한다.
- 앱은 서버가 반환한 현재 활성 Session으로 상태를 동기화한다.

## 10. 앱 생명주기와 세션 복원

### 10.1 Background 전환

우선순위: P0

- RUNNING Session의 기준 시각은 유지한다.
- 초 단위 JavaScript 실행이 계속된다고 가정하지 않는다.
- Session 목표 종료 시점의 로컬 알림을 사용한다.

### 10.2 Foreground 복귀

우선순위: P0

- 현재 활성 Session을 로컬 상태와 서버 상태에서 확인한다.
- RUNNING이면 현재 시각을 이용해 표시 시간을 다시 계산한다.
- PAUSED이면 accumulatedSeconds를 표시한다.
- 서버 상태가 클라이언트보다 최신이면 서버를 기준으로 복원한다.

### 10.3 앱 강제 종료 후 재실행

우선순위: P0

- 로그인 세션을 복원한다.
- 서버에서 활성 Session을 조회한다.
- 존재하면 전역 미니 타이머와 Timer 화면을 복원한다.
- 종료 예정 시각이 이미 지났다면 사용자에게 해당 Session 처리 상태를 보여준다.

## 11. 알림

### 11.1 알림 권한

우선순위: P0

- 필요한 시점에 알림 권한을 요청한다.
- 거부된 경우 타이머 자체는 정상 동작해야 한다.
- 설정에서 현재 알림 사용 상태를 안내한다.

### 11.2 Local Notification

우선순위: P0

알림 대상:

- Focus 목표 시간 도달
- Short Break 목표 시간 도달
- Long Break 목표 시간 도달

규칙:

- Session 시작 또는 Resume 시 알림을 예약한다.
- Pause, Complete, Discard 시 기존 예약을 취소한다.
- Resume 시 남은 시간에 맞춰 새 알림을 예약한다.
- 알림을 누르면 관련 Timer 화면으로 진입한다.

### 11.3 Push Notification

우선순위: P2

개인용 MVP에서는 서버 Push가 핵심 흐름에 필요하지 않다. 향후 서버 이벤트가 필요해질 때 도입한다.

```text

```

분류:

- actual < planned: 계획보다 적게 사용
- actual = planned: 계획과 동일
- actual > planned: 계획보다 많이 사용
- scheduleBlockId 없음: 계획 외 작업

## 17. 서버 검증과 동시성

### 17.1 사용자 소유권

우선순위: P0

- 모든 개인 리소스 조회와 변경에서 user_id를 인증 사용자와 비교한다.
- 클라이언트에서 전달한 user_id를 권한 판단 기준으로 신뢰하지 않는다.
- 다른 사용자의 Todo, Schedule, Session, Settings를 조회하거나 수정할 수 없다.

### 17.2 Todo 계층 검증

우선순위: P0

- 최대 depth 검증은 서버에서 수행한다.
- 순환 참조를 막는다.
- 부모 Todo의 소유권을 확인한다.
- 부모 이동으로 자식 depth가 2를 초과하는지 검사한다.

### 17.3 Session 상태 전이

허용 전이:

```text
RUNNING -> PAUSED
RUNNING -> COMPLETED
RUNNING -> DISCARDED
PAUSED -> RUNNING
PAUSED -> COMPLETED
PAUSED -> DISCARDED
```

COMPLETED와 DISCARDED는 종료 상태이며 기본적으로 다시 실행 상태로 되돌리지 않는다.

### 17.4 중복 시작 방지

우선순위: P0

동시에 Focus 시작 요청이 여러 번 도착해도 활성 Session은 하나만 생성되어야 한다. 앱 버튼 비활성화만으로 막지 않고 서버와 DB에서 보장한다.

## 18. 네트워크와 오류 처리

### 18.1 조회 실패

- 이전에 성공적으로 조회한 캐시가 있으면 즉시 버리지 않는다.
- 사용자가 재시도할 수 있는 UI를 제공한다.
- 인증 만료와 일반 네트워크 오류를 구분한다.

### 18.2 Mutation 실패

- Todo, Schedule, Session 상태 변경 실패를 사용자에게 알린다.
- 서버에 반영되지 않은 상태를 성공한 것처럼 확정하지 않는다.
- 낙관적 업데이트를 사용하는 경우 실패 시 이전 상태로 복원한다.

### 18.3 타이머 네트워크 실패

타이머는 작업 중 가장 중요한 상태다.

- 화면 갱신 자체는 네트워크 연결이 끊겨도 기준 시각으로 계속 계산할 수 있다.
- 상태 변경 요청이 실패하면 로컬에서 실패 상태를 보존하고 재시도할 수 있게 한다.
- 서버와 다시 연결되면 활성 Session을 조회해 충돌 여부를 확인한다.

완전한 오프라인 우선 동기화 엔진은 MVP에 포함하지 않는다.


- Resume 후 기존 누적 시간에서 이어진다.
- Complete 시 실제 기록 시간이 확정된다.
- Pause, Complete, Discard 시 잘못된 종료 알림이 남지 않는다.

## 25. 핵심 설계 원칙

1. Expo 앱 하나가 Mise Table의 핵심 제품이다.
2. App은 Node.js API를 통해서만 서버 데이터에 접근한다.
3. Todo는 계획과 실제 기록을 연결하는 기준 단위다.
4. 시간표는 강제가 아니라 비교 기준이다.
5. 계획과 다른 작업을 시작해도 막지 않는다.
6. Focus는 Todo에 연결한다.
7. 사용자당 활성 Session은 하나만 허용한다.
8. 사용자가 Todo 완료 여부를 직접 결정한다.
9. Break는 Focus와 분리해 기록한다.
10. 타이머 정확성은 백그라운드 JavaScript 지속 실행에 의존하지 않는다.
11. 데이터 정합성과 권한은 클라이언트가 아니라 서버에서 보장한다.
12. 실제 성능 문제가 확인되기 전 Redis나 집계 시스템을 추가하지 않는다.

## 26. SDD 개발 프로세스

### 26.1 기본 원칙

Mise Table은 SDD 기반으로 개발한다.

- 구현 전에 기능 명세를 확정한다.
- 명세는 사용자 요구사항뿐 아니라 Domain Rule, API Contract, DB Constraint, State Transition, Acceptance Criteria, Test Spec을 포함한다.
- 구현 계획과 Task는 확정된 Spec에서 파생한다.
- 요구사항 변경 시 코드보다 관련 Spec을 먼저 수정한다.
- 구현과 Spec의 불일치를 완료 상태로 두지 않는다.

### 26.2 기능별 문서 흐름

각 기능은 아래 흐름으로 구체화한다.

```text
1. Feature Spec
2. Domain Rule
3. API Contract
4. DB / Constraint
5. State Transition
6. Acceptance Criteria
7. Test Spec
8. Implementation Plan
9. Tasks
10. App / Server Implementation
11. Verification
```

모든 기능에 동일한 크기의 문서를 강제하지 않는다. 단순 조회 기능은 필요한 명세만 짧게 작성하고, Timer, Auth, Todo Tree처럼 상태와 정합성이 중요한 기능은 계약과 상태 전이를 상세하게 작성한다.

### 26.3 Feature Spec 필수 항목

```text
목적
사용자 시나리오
입력과 출력
정상 흐름
예외 흐름
권한
Domain Rule
Acceptance Criteria
```

### 26.4 API Contract 규칙

App과 Server 사이의 API는 구현 전에 다음을 확정한다.

- HTTP Method와 Path
- Request Param, Query, Body
- Response Body
- 인증 필요 여부
- 성공 상태
- 오류 코드와 의미
- 상태 변경 조건
- 멱등성이 필요한 요청 여부

NestJS 구현과 API 문서는 동일한 계약을 표현해야 한다. App은 임의의 응답 형태를 가정하지 않는다.

### 26.5 DB와 Domain Rule

다음 규칙은 명세와 DB 설계에 함께 반영한다.

- Todo depth 최대 3단계
- Todo Tree 순환 참조 금지
- 사용자 소유권
- Schedule Block의 종료 시각이 시작 시각보다 늦음
- Focus는 Todo 필수
- 사용자당 활성 Session 최대 1개
- Session 상태 전이 제한
- 삭제된 Todo의 과거 기록 보존
- DISCARDED Session의 기본 통계 제외

애플리케이션 검증만으로 충분하지 않은 정합성 규칙은 가능한 범위에서 DB Constraint와 Transaction으로 보장한다.

### 26.6 State Transition 명세

Timer와 Session은 코드 작성 전에 상태 전이를 명세한다.

```text
RUNNING -> PAUSED
RUNNING -> COMPLETED
RUNNING -> DISCARDED
PAUSED -> RUNNING
PAUSED -> COMPLETED
PAUSED -> DISCARDED
```

각 전이에는 다음을 함께 정의한다.

- 전이 가능 조건
- 서버에서 변경할 필드
- duration 계산 방식
- 로컬 알림 예약 또는 취소
- App Query Cache 갱신
- 네트워크 실패 시 UI 상태

### 26.7 Acceptance Criteria

Acceptance Criteria는 구현 완료 여부를 판단할 수 있을 만큼 구체적으로 작성한다.

예시:

```text
Given 사용자의 RUNNING Session이 존재할 때
When 새로운 Focus Session 시작을 요청하면
Then 서버는 새 Session을 생성하지 않고 기존 활성 Session 정보를 반환한다.
```

### 26.8 Test Spec

Test Spec은 최소한 다음 범위를 구분한다.

- Domain Rule 단위 테스트
- Service 상태 전이 테스트
- DB Constraint와 동시성 테스트
- API Contract 통합 테스트
- App 주요 사용자 흐름 테스트
- Timer 백그라운드 복원 테스트

테스트의 목적은 구현 코드 자체가 아니라 Spec의 규칙이 실제로 지켜지는지 확인하는 것이다.

### 26.9 변경 관리

기능 요구사항이 변경되면 다음 순서로 반영한다.

```text
Spec
-> 관련 Domain / API / DB / State 문서
-> Acceptance Criteria
-> Test Spec
-> Plan
-> Tasks
-> Implementation
```

문서와 구현의 차이를 발견하면 단순히 코드를 현재 문서에 맞추는 것이 아니라, 실제로 합의된 최신 요구사항이 무엇인지 먼저 판단한다. 요구사항 자체가 변경된 경우 Spec부터 갱신한다.

### 26.10 SDD 기준 Definition of Done

기능은 다음 조건을 모두 만족해야 완료다.

- Feature Spec 확정
- 관련 Domain Rule 반영
- API Contract와 구현 일치
- DB Constraint와 구현 일치
- Acceptance Criteria 충족
- Test Spec의 필수 케이스 통과
- App과 Server의 상태 해석 일치
- Spec, Plan, Tasks와 실제 구현 사이의 미해결 불일치 없음
