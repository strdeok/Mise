# Mise Table 기획서

## 1. 서비스 개요

Mise Table은 오늘 해야 할 일을 시간표에 배치하고, 각 Todo에 실제로 사용한 시간을 집중 세션으로 기록하는 모바일 작업 시간관리 앱이다.

사용자는 해야 할 일을 최대 3단계로 정리하고, 하루 시간표에 작업 블록을 배치한 뒤, 실제 작업을 시작할 때 해당 Todo의 타이머를 실행한다. 기록된 집중 시간은 Todo 계층에 따라 상위 항목으로 합산되며, 주간과 월간 통계에서 계획한 시간과 실제 사용한 시간을 비교할 수 있다.

핵심 흐름은 다음과 같다.

```text
할 일 작성 -> 하루 계획 -> 집중 실행 -> 실제 시간 기록 -> 회고
```

키친 타이머의 아이디어는 여러 작업의 순서와 시간을 미리 준비하고 실행한다는 구조에서만 가져온다. UI는 요리 앱처럼 표현하지 않고 미니멀한 생산성 도구로 설계한다.

## 2. 한 문장 정의

오늘 할 일을 시간표에 배치하고, 실제로 쓴 시간을 Todo별 집중 세션으로 기록해 계획과 실제 시간의 차이를 보여주는 모바일 작업 시간관리 앱.

## 3. 플랫폼 전략

MVP는 모바일 앱 하나에 집중한다.

- iOS와 Android를 Expo 기반 단일 코드베이스로 개발한다.
- 웹 앱과 데스크탑 앱은 MVP에서 개발하지 않는다.
- Tauri, 플로팅 데스크탑 타이머, 메뉴바, 트레이 기능은 현재 범위에서 제외한다.
- 모바일 앱이 Todo 관리, 시간표 작성, 타이머 실행, 통계 확인을 모두 담당한다.
- 서버 데이터의 진입점은 Node.js API로 통일한다.

모바일은 기존 기획의 보조 플랫폼이 아니라 Mise Table의 본체다.

## 4. 타깃 사용자

### 4.1 주요 사용자

- 개발자
- 직장인
- 학생
- 개인 작업 시간이 중요한 지식 노동자

### 4.2 사용자 특성

- 하루에 여러 작업을 전환하며 진행한다.
- Todo를 완료했는지만이 아니라 실제로 얼마나 시간이 들었는지 알고 싶어 한다.
- 캘린더에 계획은 세우지만 실제 하루가 계획대로 흘렀는지는 파악하기 어렵다.
- Pomodoro를 사용하더라도 각 집중 시간이 어떤 작업에 쓰였는지 나중에 확인하기 어렵다.
- PC 앞에 있지 않을 때도 빠르게 작업을 추가하거나 타이머를 제어하고 싶어 한다.

## 5. 문제 정의

### 5.1 Todo 앱의 한계

Todo 앱은 무엇을 해야 하는지는 보여주지만, 실제로 각 작업에 얼마나 많은 시간이 들어갔는지는 충분히 보여주지 않는다. `Todo API 개발`을 완료하더라도 30분이 걸렸는지 4시간이 걸렸는지를 알기 어렵다.

### 5.2 타이머 앱의 한계

일반적인 Pomodoro 앱은 집중 시간을 측정하지만 그 시간을 작업 구조와 연결하기 어렵다. 여러 세션이 쌓여도 어떤 프로젝트와 Todo에 시간이 사용되었는지를 다시 정리해야 한다.

### 5.3 캘린더의 한계

캘린더는 계획에는 강하지만 실제 작업 기록과 계획을 자동으로 비교하지 않는다. 사용자는 계획한 1시간짜리 작업이 실제로 40분이 걸렸는지 2시간이 걸렸는지 별도로 추적해야 한다.

### 5.4 기록의 분산

Todo, 캘린더, 타이머를 각각 사용하면 동일한 작업을 여러 서비스에서 반복 관리하게 된다. Mise Table은 Todo를 공통 단위로 사용해 계획과 실제 기록을 한 흐름으로 연결한다.

## 6. 핵심 가치

1. 오늘 해야 할 일을 빠르게 확인한다.
2. Todo를 하루 시간표에 직접 배치한다.
3. Todo에 실제 사용한 시간을 집중 세션으로 기록한다.
4. 하위 Todo의 시간을 상위 Todo에 합산한다.
5. 계획 시간과 실제 시간을 비교한다.
6. 집중과 휴식 시간을 하나의 작업 리듬으로 기록한다.
7. 사용자를 평가하거나 통제하지 않고 실제 시간 사용을 보여준다.

## 7. 제품 포지셔닝

| 구분 | 일반적인 역할 | Mise Table |
| --- | --- | --- |
| Todo 앱 | 할 일과 완료 여부 관리 | Todo와 실제 투자 시간 연결 |
| Pomodoro 앱 | 집중 세션 측정 | Todo에 귀속되는 집중 세션 |
| 캘린더 앱 | 일정 계획 | 하루 작업 시간표와 실제 기록 비교 |
| 시간 추적 앱 | 사용 시간 기록 | 오늘 할 일과 계획을 중심으로 기록 |

차별점은 `계획한 작업 시간`과 `실제로 사용한 시간`을 동일한 Todo 기준으로 연결하는 데 있다.

## 8. 핵심 사용자 경험

### 8.1 하루 시작

사용자는 Today 화면에서 오늘 해야 할 Todo를 확인하거나 새로 추가한다. 필요한 Todo는 최대 3단계로 정리한다.

### 8.2 하루 계획

Schedule 화면에서 Todo를 특정 시간대에 배치한다. 시간표는 강제가 아니라 나중에 실제 사용 시간과 비교하기 위한 계획이다.

### 8.3 작업 실행

시간 블록 또는 Todo에서 집중을 시작한다. 실행 중인 타이머는 앱 전역에서 미니 타이머로 계속 표시한다. 미니 타이머를 누르면 전체 타이머 화면으로 이동한다.

### 8.4 계획 변경

사용자는 시간표와 다른 Todo를 언제든 시작할 수 있다. 이 경우 해당 세션은 계획 외 작업으로 기록한다.

### 8.5 회고

Stats에서 Todo별 실제 시간, 상위 프로젝트 합산 시간, 계획 시간과 실제 시간의 차이를 확인한다.

## 9. 핵심 기능

### 9.1 계정 및 동기화

- 이메일 기반 회원가입과 로그인
- JWT 기반 인증
- 앱 재실행 시 로그인 상태 복원
- 사용자별 데이터 분리
- Todo, 시간표, 세션, 설정을 서버에 저장

MVP는 단일 모바일 앱이지만 데이터는 서버를 기준으로 관리해 기기 변경에도 기록을 유지한다.

### 9.2 Todo 관리

Todo는 최대 3단계 depth를 가진다.

```text
프로젝트
└─ 작업
   ├─ 세부 작업
   └─ 세부 작업
```

- Todo 생성, 수정, 완료, 삭제
- 부모 Todo 지정
- 최대 3단계 계층
- 오늘 할 일 지정
- 사용자 지정 정렬
- Todo에서 바로 집중 시작
- 하위 Todo의 집중 시간을 상위 Todo에 합산
- 상위 Todo에 직접 기록한 시간도 합산

### 9.3 하루 시간표

- 날짜별 Day View
- 시간 블록 생성, 수정, 삭제
- Todo 연결
- 시작 시간과 종료 시간 설정
- 시간 블록에서 바로 집중 시작
- 계획 시간과 실제 기록 시간 표시
- 시간표와 무관한 작업 시작 허용

모바일 MVP에서는 정밀한 드래그 리사이즈보다 탭 기반 생성과 시간 선택을 우선한다. 제스처 기반 편집은 사용성 검증 후 확장한다.

### 9.4 집중 세션

- Focus 시간 사용자 지정
- 시작, 일시정지, 재개, 완료, 폐기
- 동시에 실행 가능한 세션은 사용자 기준 1개
- 중간에 중단한 시간도 저장 가능
- 시간표에서 시작한 세션은 해당 schedule block과 연결
- 계획 없이 시작한 세션은 계획 외 작업으로 기록

### 9.5 휴식 세션

- Short Break
- Long Break
- 기본 휴식 시간 사용자 설정
- 휴식 종료 알림
- 휴식 시간은 집중 시간과 분리해 통계에 기록
- 필요하면 직전 Focus 세션과 연결

### 9.6 모바일 알림

- Focus 종료 알림
- Short Break 종료 알림
- Long Break 종료 알림
- 알림을 누르면 관련 타이머 화면으로 이동

타이머 정확도를 백그라운드 JavaScript 실행에 의존하지 않는다. 시작 시각과 누적 시간을 저장하고 현재 시각과의 차이로 화면 시간을 계산한다. 예정된 종료 시점에는 로컬 알림을 예약한다.

### 9.7 통계

- 주간 총 집중 시간
- 월간 총 집중 시간
- 총 휴식 시간
- Focus 세션 수
- Todo별 직접 기록 시간
- 하위 Todo 포함 합산 시간
- 상위 프로젝트별 사용 시간
- 계획 시간과 실제 시간 비교
- 계획 외 작업 시간

통계는 사용자를 평가하는 점수 기능이 아니라 실제 시간 사용을 관찰하는 기능으로 설계한다.

### 9.8 월간 캘린더

월간 캘린더는 MVP 후반의 P1 기능으로 둔다.

- 날짜별 계획 존재 여부
- 날짜별 총 집중 시간
- 날짜 선택 시 해당 날짜의 Day View 이동

Google Calendar 연동은 MVP에서 제외한다.

## 11. 타이머 설계 원칙

타이머는 앱 프로세스에서 매초 증가한 숫자를 데이터의 기준으로 사용하지 않는다.

서버와 로컬에는 최소한 다음 상태를 유지한다.

```text
started_at
paused_at
accumulated_seconds
target_seconds
status
```

실행 중 화면에 표시할 시간은 현재 시각과 저장된 기준 시각으로 계산한다. 앱이 백그라운드로 이동하거나 다시 실행되어도 저장된 세션 상태를 기준으로 복원한다.

- DB가 세션 상태의 최종 기준이다.
- 클라이언트의 1초 interval은 화면 표시 갱신 용도로만 사용한다.
- 세션 시작, 일시정지, 재개, 완료 시 서버 상태를 변경한다.
- Focus 또는 Break 시작 시 종료 예정 시각에 로컬 알림을 예약한다.
- 세션을 일시정지, 완료, 폐기하면 기존 예약 알림을 취소하거나 다시 예약한다.

## 15. 핵심 사용자 플로우

### 15.1 기본 흐름

```text
1. 로그인한다.
2. Today에서 오늘 Todo를 작성한다.
3. 필요한 Todo를 최대 3단계로 정리한다.
4. Schedule에서 Todo를 시간 블록에 배치한다.
5. 시간 블록 또는 Todo에서 Focus를 시작한다.
6. 작업 중에는 미니 타이머로 현재 상태를 확인한다.
7. Focus를 완료한 뒤 휴식 또는 다음 작업을 선택한다.
8. 작업이 끝나면 Todo를 직접 완료 처리한다.
9. Stats에서 계획 시간과 실제 시간을 확인한다.
```

### 15.2 계획 외 작업

```text
1. 현재 필요한 Todo를 직접 선택한다.
2. 시간표와 관계없이 Focus를 시작한다.
3. 완료하거나 중단한다.
4. 저장된 시간은 실제 기록에 반영된다.
5. Stats에서는 계획 외 작업으로 구분한다.
```

### 15.3 백그라운드 이동

```text
1. Focus를 시작한다.
2. 앱이 백그라운드로 이동한다.
3. 클라이언트는 초 단위 실행을 계속 유지하려 하지 않는다.
4. 예정 종료 시각에 로컬 알림이 발생한다.
5. 앱을 다시 열면 저장된 started_at과 세션 상태를 기준으로 시간을 복원한다.
```

## 17. 성공 기준

### 정성적 기준

- 사용자가 하루 시작 전에 Today와 Schedule을 확인한다.
- Todo에서 바로 Focus를 시작하는 흐름이 자연스럽다.
- 앱을 백그라운드로 보낸 뒤에도 타이머 기록을 신뢰할 수 있다.
- 하루 또는 일주일이 끝난 뒤 계획과 실제 시간의 차이를 이해할 수 있다.
- 사용자가 `오늘 시간이 어디에 쓰였는지 알겠다`고 느낀다.

### 초기 정량 지표

- 하루 1회 이상 Todo 생성 또는 완료
- 하루 2회 이상 Focus 세션 기록
- 주 3일 이상 사용
- 주간 Stats 화면 조회
- Schedule을 작성한 날의 Focus 세션 기록률

## 18. 주요 리스크

### 18.1 흔한 Todo 또는 Pomodoro 앱으로 보이는 문제

Todo 기능과 타이머 자체를 경쟁력으로 내세우지 않는다. 메시지와 UI 모두 `계획 -> 실행 -> 실제 기록 비교`에 집중한다.

### 18.2 모바일 시간표 편집의 복잡성

PC식 정밀 드래그 UI를 그대로 옮기지 않는다. MVP에서는 시간 블록 추가 버튼과 시간 선택을 기본으로 하고, 제스처 편집은 이후 검증한다.

### 18.3 백그라운드 타이머 정확성

백그라운드에서 JavaScript 타이머가 계속 실행된다고 가정하지 않는다. 절대 시각을 저장하고 화면 복귀 시 재계산하며 종료 알림은 OS 예약 알림을 사용한다.

### 18.4 범위 증가

웹, 데스크탑, 외부 캘린더, AI 기능을 MVP에 다시 추가하지 않는다. 모바일에서 핵심 루프를 검증한 뒤 확장 여부를 판단한다.

## 19. 설계 원칙

1. 모바일 앱이 제품의 본체다.
2. Todo 앱이 아니라 Todo 기반 작업 시간관리 앱이다.
3. Pomodoro 앱이 아니라 Todo와 연결된 실제 시간 기록 앱이다.
4. 시간표는 사용자를 통제하기 위한 기능이 아니라 실제 기록과 비교하기 위한 기준이다.
5. 계획과 다르게 작업해도 막지 않는다.
6. 동시에 하나의 실행 세션만 허용한다.
7. 휴식도 작업 리듬의 일부로 기록한다.
8. 타이머의 정확성을 앱 프로세스의 지속 실행에 의존하지 않는다.
9. 앱은 DB에 직접 접근하지 않고 Node.js API를 통해 데이터에 접근한다.
10. 키친 타이머 컨셉은 구조에만 사용하고 UI는 차분한 생산성 도구로 유지한다.

## 20. 요약

Mise Table은 Expo 기반 모바일 작업 시간관리 앱이다. 사용자는 Todo를 작성하고 하루 시간표에 배치한 뒤, Focus와 Break 세션으로 실제 사용 시간을 기록한다. 기록은 Todo 계층에 따라 합산되며 주간과 월간 통계에서 계획한 시간과 실제 사용 시간을 비교할 수 있다.

클라이언트는 Expo와 React Native로 개발하고, 서버는 Node.js와 NestJS, 데이터베이스는 PostgreSQL과 Prisma를 사용한다. 웹, Tauri 데스크탑, Supabase 직접 접근 구조는 현재 MVP에서 사용하지 않는다.

## 21. SDD 개발 원칙

Mise Table은 SDD를 기본 개발 방식으로 사용한다. 구현을 먼저 만든 뒤 문서를 맞추는 방식이 아니라, 기능의 동작과 계약을 명세에서 먼저 확정한 뒤 App과 Server를 구현한다.

기본 흐름은 다음과 같다.

```text
기획
-> Feature Spec
-> Domain Rule
-> API Contract
-> DB Constraint
-> State Transition
-> Acceptance Criteria
-> Test Spec
-> Plan / Tasks
-> Implementation
-> Verification
```

### 21.1 명세 우선

- 새로운 기능은 구현 전에 Feature Spec을 작성한다.
- 사용자 행동, 정상 흐름, 예외 흐름, 권한, 상태 변화를 명세에 먼저 정의한다.
- App과 Server가 공유하는 API 요청과 응답, 오류 계약을 구현 전에 확정한다.
- DB 제약과 동시성 규칙은 애플리케이션 코드만이 아니라 데이터 정합성 관점에서 명시한다.
- Timer처럼 상태 전이가 중요한 도메인은 허용 상태와 전이를 먼저 정의한다.

### 21.2 변경 규칙

요구사항 또는 동작이 바뀌면 다음 순서를 지킨다.

```text
Spec 변경
-> 영향받는 Contract / Rule / Acceptance Criteria 변경
-> Plan / Tasks 변경
-> 구현 변경
-> 테스트로 명세 충족 확인
```

코드와 명세가 충돌할 경우 현재 합의된 요구사항을 기준으로 명세를 먼저 수정하고 구현을 맞춘다. 코드 변경만 하고 명세를 뒤에 방치하지 않는다.

### 21.3 핵심 명세 대상

초기에는 다음 도메인의 명세를 우선 확정한다.

1. Auth와 Token 수명주기
2. Todo Tree와 3단계 제약
3. Today와 Todo 날짜 배치
4. Schedule Block
5. Focus와 Break Session
6. Timer 상태 전이와 백그라운드 복원
7. 사용자당 활성 Session 1개 제약
8. 계획 시간과 실제 시간 계산
9. 통계 집계 규칙
10. 알림 예약과 취소 규칙

### 21.4 완료 기준

기능 완료는 화면이나 API가 동작하는 것만으로 판단하지 않는다.

- Spec의 Acceptance Criteria 충족
- API Contract와 실제 응답 일치
- DB Constraint와 Domain Rule 일치
- 상태 전이 규칙 위반 없음
- Test Spec에 정의한 핵심 케이스 통과
- 구현 이후 Spec과 코드 사이 불일치 없음

이 조건을 만족해야 해당 기능을 완료로 본다.
